# 3万のPCでClaude Codeに動画を作らせてみた：実行環境・音声合成・レンダリングの舞台裏

この動画では、本体RAM 4GBのChromebookという、動画制作には本来向かないとされる環境でAIエージェント（Claude Code）に指示を出し、動画制作パイプラインを構築しました。この文書では、その具体的な構成を手順として再現可能な形でまとめています。

## 1. 実行環境について：Chromebook × Linux開発環境

### 結論
- 使っているのは一般的なノートPCではなく、**Chromebook**（本体RAM 4GB）
- Chromebookに搭載されているLinux開発環境（Crostini、ChromeOS上でLinuxアプリを動かす仕組み）の中で作業しているため、実際にコードが動く空間から見えるメモリは**約2.6GB**
- つまり「本体4GB」と「実際に使える2.6GB」という二段階の制約がある

### なぜ二段階になるのか
- Chromebook本体のRAM4GBは、ChromeOS自体の動作や、ChromeOSからLinux環境を動かす仕組み（仮想化）にも使われる
- Linux開発環境は、ChromeOS上で動く仮想マシン（VM）として実装されている。以下のコマンドで、今使っている環境がVMであることが確認できる
  ```bash
  hostnamectl
  # Chassis: vm
  # Virtualization: kvm
  ```
- そのVMに割り当てられているメモリを見ると、本体の4GBよりも少ない
  ```bash
  free -h
  # Mem: 2.6Gi
  ```

### なぜこれが動画制作の文脈で重要か
- 動画編集・レンダリングは一般に高スペックPCが前提とされる作業
- しかし今回のパイプラインは、重い処理（音声合成・映像レンダリング）を以下で説明する通り「軽量化」「クラウドへのオフロード」で分散しているため、Chromebookという本来動画編集には向かないとされる機材でも成立している
- スペックを言い訳にせず、設計（何をローカルでやり、何を外部に任せるか）で制約を突破できる、という動画全体の主張の土台になっている部分

### 確認に使ったコマンド（そのまま再現可能）
```bash
free -h                              # 現在使えるメモリ量
cat /proc/meminfo | head -3          # メモリ総量の詳細
hostnamectl                          # VMかどうか、仮想化方式
systemd-detect-virt                  # 仮想化技術の種類（kvm等）
```

## 2. VOICEVOXの動かし方（低スペック環境向け軽量構成）

### 結論
- 公式のVOICEVOX GUI版（Electronアプリ、約1.9GB）は起動が重く、低スペック環境では都度の起動・終了が現実的でない
- VOICEVOX Core（C API）とONNX Runtimeそのものは合計約22MBと小さいが、音声モデル（.vvmファイル）と辞書（OpenJTalk、約103MB）を含めた実際のディスク使用量は約305MB、起動時の常駐メモリは約525MB（`du -sh`・`ps -o rss`で実測）。それでもGUI版の1.9GBに比べれば軽量
- これをPythonから直接呼び出すFastAPIサーバーを自作し、ヘッドレスで動かすことで軽量化した
- これにより、コマンド一発でバックグラウンド起動・停止できる音声合成APIとして、動画制作パイプラインに組み込んでいる

### なぜGUI版を使わないのか
- GUI版はElectron製で1.9GBあり、起動のたびにメモリと時間を消費する
- 動画制作は音声合成を何十回・何百回も繰り返す作業（セリフ単位でレンダリングするため）なので、GUIを都度立ち上げてkillする運用は非効率
- VOICEVOX Core自体（音声合成エンジンの中核）はC APIとして提供されており、GUIなしでも呼び出せる

### 構成要素
- **VOICEVOX Core（C API）**: 音声合成の中核エンジン
- **ONNX Runtime**: Core内部の推論処理に使われる軽量な推論エンジン（Core本体と合わせて約22MB）
- **自作Pythonラッパー（FastAPI）**: C APIをHTTPサーバーとして公開する薄いレイヤー
- **uvicorn**: FastAPIアプリを動かすASGIサーバー
- **音声モデル（.vvmファイル）**: キャラクターごとの声質データ。ずんだもんの場合、全8スタイル（ノーマル/あまあま/ツンツン/セクシー/ささやき/ヒソヒソ/ヘロヘロ/なみだめ）を使うには複数の.vvmファイルが必要（3ファイルで約180MB）
- **辞書（OpenJTalk）**: 形態素解析・読み推定に使う辞書データ（約103MB）

### 起動・停止
シェルスクリプト1本で管理する。
```bash
./run.sh start   # バックグラウンドでサーバー起動
./run.sh status  # 起動状態を確認
./run.sh stop    # 停止
```
内部では`uvicorn server:app --host 127.0.0.1 --port 50021`をバックグラウンドプロセスとして起動し、PIDをファイルに保存して管理している。GUIアプリのプロセス管理を、シェルスクリプトによる宣言的な起動/停止に置き換えたイメージ。

### API呼び出し
ローカルのHTTPエンドポイント（例: `/synthesize`）にテキストを渡すと音声ファイルが返る、というシンプルな構成。読み上げの自然さを調整するため、以下のパラメータを実装・調整している。
- `intonation_scale`: 抑揚の強さ
- `pause_scale`: 読点・句点の間（ポーズ）の長さ
- `speed_scale`: 話速
- `pitch_scale`: 音の高さ

デフォルトの値は、実際に聴き比べながら「不自然に聞こえないか」を基準にチューニング済み。

### つまずいたポイント（つまずきそうな人向け）
- キャラクター名（今回は「ずんだもん」）が形態素解析辞書に登録されていないと、助詞の読みまで巻き込んで誤読することがある。ユーザー辞書に固有名詞として登録することで解消できる
- 読点と句点のポーズは、音声合成エンジン側の内部データだけでは区別できない場合がある。テキスト側の記号と突き合わせて自前で処理を挟む必要がある

### 動画パイプラインへの組み込み
このAPIサーバーを、動画のシーンごとにレンダリングスクリプトから呼び出し、「テキスト→音声ファイル」を自動生成している。動画編集ソフトを手動操作する代わりに、コードから一括で音声とタイミングを生成する構成。

## 3. 動画レンダリングの動かし方（低スペック環境向け・AWS Lambdaオフロード構成）

### 結論
- 動画レンダリング（コンポジションを実際のmp4に書き出す処理）はCPU・メモリを大量に消費する重い作業で、RAM2.6GBのローカル環境で完結させるのは現実的でない
- Remotion（React/TypeScriptで動画を宣言的に記述するフレームワーク）の公式機能`@remotion/lambda`を使い、レンダリングだけをAWS Lambda上のクラウド関数にオフロードする構成にした
- ローカル側は「コードを書く」「レンダリング命令を送る」だけの薄いクライアントになり、重い計算処理を一切引き受けない

### なぜAWS Lambdaなのか
- Remotionの動画は最終的にコード（React コンポーネント）なので、そのままクラウドの関数として実行できる。ローカルGPUやハイスペックCPUを持っている必要がない
- Lambdaは関数を並列に何個も同時実行できるため、動画を分割してレンダリングし、後から結合する運用と相性が良い
- 使った分だけ課金される従量課金モデルなので、低頻度の個人利用でも導入しやすい

### 構成要素
- **S3バケット**: レンダリング対象のコード（サイト）と、出力された動画ファイルの置き場
- **Lambda関数**: 実際にレンダリング処理を実行するクラウド上の関数。呼び出すたびに実行され、終わったら課金も止まる
- **IAMポリシー**: 使う権限を必要最小限（S3の特定バケットへの読み書き、特定命名規則のLambda関数の呼び出し、ログ出力）に絞ったアクセス権限。権限を絞ることで、認証情報が漏れた場合の被害範囲を限定できる
- **認証情報（.env）**: AWSのアクセスキーをローカルの`.env`ファイルに保存し、gitの管理対象からは除外する

### 音声ファイルはどう渡っているか
セリフごとの音声（VOICEVOXが生成したwav）は、Remotionの「静的アセット」の仕組み（`staticFile()`）でコンポーネントから参照している。この方式では、参照するファイルは**Lambda上のコードと同じS3バンドルに含まれている必要がある**。つまり音声ファイルを、動的なURLやBase64としてレンダリング時に渡しているのではなく、**サイトのデプロイ（アップロード）に含める**ことで届けている。この制約により、新しいセリフの音声を使う以上、シーンごとに（コードが変わっていなくても）サイトを再デプロイする必要がある。

### デプロイ・レンダリングの流れ
1. **サイトのデプロイ（毎回・音声ファイルを含めるため）**: ローカルのRemotionプロジェクト（コード＋直前に生成した音声ファイル）をS3にアップロードする
   ```bash
   npx remotion lambda sites create --site-name=remotion-app
   ```
   コード部分はTypeScriptのビルド(トランスパイル)を伴うため瞬間的にメモリを数百MB単位で消費するが、音声ファイル自体は数十KB〜数百KB程度と小さく、支配的なコストではない。デプロイ処理は専用スクリプトに切り出し、コマンド1つで完結させている（重複コードを避ける目的で、レンダリング用スクリプトからも同じスクリプトを呼び出している）。
2. **レンダリング実行**: デプロイ済みのサイトに対して、セリフのテキストや音声ファイル名などシーン固有の情報を`--props`で渡してLambda上でレンダリングを実行する
   ```bash
   npx remotion lambda render remotion-app <コンポジション名> <出力先> \
     --codec=h264 \
     --concurrency=<並列数> \
     --props='<シーンごとのパラメータをJSONで>'
   ```
3. 完成した動画がローカルにダウンロードされる

並列数（concurrency）は、AWSアカウントの同時実行数の上限内に収まる値に調整する（上限に対して余裕を持たせておくと安定する）。

> [!note] 検討したが採用していない構成
> 「音声ファイルを別途S3にアップロードし、そのURLだけを`--props`で渡す」方式にすれば、コード変更がない限りサイトの再デプロイ自体が不要になり、さらに軽量化できる可能性がある。現状は`staticFile()`によるサイトバンドル方式のままで、この最適化は今後の検討課題。

### コスト管理の考え方
- 個人開発規模の低頻度利用が前提のため、事前に予算アラートを設定した上で運用し、想定外の課金が発生してもすぐ気づける状態にしている
- レンダリングはシーン単位（セリフ1本ごと）で短く区切って実行し、あとで結合する運用にすることで、1回あたりの処理時間・コストを小さく保っている

### 動画パイプラインへの組み込み
デプロイ処理を専用スクリプトに切り出し、レンダリング用スクリプトから呼び出す形で共通化している。

1. ローカルのVOICEVOXエンジンを起動確認・起動
2. そのエンジンでセリフを音声合成（`public/`配下に音声ファイルが生成される）
3. サイトを再デプロイ（音声ファイルを含む最新の`public/`をS3にアップロード）
4. AWS Lambda上でレンダリングを実行し、完成した動画をローカルに出力
5. （エラーの有無にかかわらず）VOICEVOXエンジンを確実に停止する。シェルの`trap`でスクリプトの終了処理として登録しておくことで、途中でエラーが起きてもプロセスが残り続けない

ローカル環境は「音声合成」「デプロイ命令」「レンダリング命令を送る」だけにメモリを使い、一番重い処理（実際の動画書き出しと、コードのビルド）はクラウド側に逃がしている、という設計。

### 「ローカル負荷がほぼ動かない」ことを自分で確認する方法
動画内では、レンダリング中もローカルのメモリ・CPUがほぼ動いていないことをターミナルの記録で示している。画像1枚を信じてもらう必要がないよう、同じ環境（Linux/Chromebook等）を持っていれば誰でも自分の手元で再現・検証できる手順をここに書いておく。

1. ターミナルを2枚開く
2. 片方で、上記の`npx remotion lambda render ...`コマンドを実行する
3. もう片方で、レンダリングが終わるまでの間、以下を実行してメモリ・CPUを監視する
   ```bash
   watch -n 1 free -h
   ```
   （CPU上位プロセスも見たい場合は`top`を別途実行する）
4. `used`（使用中メモリ）の値が、レンダリング開始前後でほとんど変化しないこと、`top`の上位プロセスに`remotion`や`render`関連の重いプロセスが出てこないことを確認する

この結果は、構成上の設計（重い処理はすべてLambda上のクラウド関数で実行され、ローカルはHTTPリクエストを送って結果を待つだけ）から論理的に導かれる帰結であり、特定の環境やタイミングに依存する偶然の結果ではない。

### 既知の制約（正直に書いておく）
この構成は万能ではなく、認識している弱点が2つある。

- **シーン数が増えるとデプロイコストが積み上がる**: 音声を含めるため毎回サイトを再デプロイする構成（前述）は、シーンが数本程度なら無視できるが、1本の動画が50〜100シーン規模になると、デプロイのたびに発生するビルド時間とS3への通信コストが無視できなくなってくる。今回の動画のようにシーン数が少ない構成では問題にならないが、今後もっと長尺・多シーンの動画を作る場合は、音声ファイルをサイトのバンドルに含めず別経路（S3への直接アップロード＋URL渡し等）で受け渡す設計に見直す必要が出てくる見込み
- **技術スタックが多岐にわたる脆さ**: Bashでのプロセス管理、Python(FastAPI)でのVOICEVOX Core呼び出し、Node.js(Remotion)での映像定義、AWS CLI経由でのLambda/S3操作、と経由する技術が多い。どこか1つのライブラリの破壊的アップデートや依存関係の崩れが、パイプライン全体を止めうる。シンプルさと引き換えに、この種の複合構成にした結果のトレードオフとして受け入れている
